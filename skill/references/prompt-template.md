## 请严格按下面四步设计用例

### 第一步：枚举输入的特征维度

系统性列出：这个模块的输入在哪些互相独立的维度上会变化？
（{{给 3-5 个方向提示，但要求对方自己补全}}……请自己补全）

把维度和每个维度的取值列成表，写在测试文件顶部注释里。

### 第二步：构造维度的两两交叉

不要只测每个维度的单独取值。对任意两个维度 A、B，取 A 的每个值 × B 的每个值。
**特别注意「本身就是特殊情况」的取值——两个特殊情况叠加时最容易出问题。**
请标注哪些用例覆盖哪一对维度的交叉。

### 第三步（重点，务必执行）：枚举每个特征「进入系统的路径」

对你在第一步列出的**每一个特征**，问自己：

> **这个特征有几种方式进入这个函数/对象？**

常见两大类：
- **路径 A：由参数控制产生** —— 调用时通过某个参数，让它在输出里产生这个特征
- **路径 B：由数据自带 / 由后续操作引入** —— 这个特征已经存在于传入的数据里，
  或者通过对同一对象的重复操作、时间推进而出现，需要被正确识别和处理

**同一个特征走这两条路径时，内部走的很可能是完全不同的代码：**
一条是「生成/初始化」逻辑，另一条是「解析/更新」逻辑。
**只测其中一条，另一条的缺陷永远碰不到。**

请对每个特征**分别构造这两类用例**。尤其注意：
- 把「已经自带该特征的数据」直接作为**输入参数**传进去
- 对**已经存在的对象/键再次操作**，而不是只测首次
- 让某个属性在**写入之后**才发生变化
- 若某特征既能由参数产生、又能由数据引入，**两条路径都必须测**
- 把「输入自带」的用例与第二步的维度交叉**结合**：构造同时自带两个特殊特征的输入

在测试函数名或 docstring 里标注每个用例走的是哪条路径（`path_a` / `path_b`）。

### 第四步：写测试

写到：`{{输出路径}}`

1. 导入方式：`{{from xxx import ...}}`
2. 每个测试函数 `test_` 开头，命名要说明测什么
3. 断言明确期望值，不要 `assert x is not None` 这种空断言
4. 不用 mock（需要可控时钟等可自己写简单可控对象）
5. **期望值必须来自「按规范/文档，这个东西应该返回什么」**，不是「某段代码会返回什么」
6. 写完**不要运行测试**，也不要根据运行结果反过来修改期望值
