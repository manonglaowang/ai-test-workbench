## 这不是变异测试的锅

先说清楚：变异测试是个好工具，它比行覆盖率严格得多。行覆盖率只问「这行代码跑到了吗」，变异测试问的是「我把这行改坏了，你的测试会失败吗」——后者才接近「测试有没有在断言」。

问题不在工具，在**它测的是什么**。

变异测试注入的是**单点变异**：把一个 `>` 改成 `>=`、删掉一个分支、改一个索引。所以它衡量的是——

> **你的测试，对「代码在单个位置上被改坏」有多敏感。**

这是一个关于**覆盖密度**的指标。

而真实 bug 长什么样？拿这次实验的靶子举例，[pypinyin 的 issue #290](https://github.com/mozillazg/python-pinyin/issues/290)：

```diff
- RE_TONE2 = re.compile(r'([aeoiuvnmê])([1-5])$')
+ RE_TONE2 = re.compile(r'([aeoiuvnmêü])([1-5])$')
```

一个正则的字符类漏了 `ü`。触发它需要**两个条件同时成立**：输入里有 `ü`/`v` 韵母，**并且**带轻声 5，比如 `lün5`。

AI 测了 40–50 种含 `ü` 的输入，测了 6–9 种含轻声 5 的输入，**两者的组合：0 个**。

单维度密度很高，交叉密度为零。**杀伤率考的正好是前者。**

## 换个项目也一样

为了排除「只是这一个项目的巧合」，我又换了 [cachetools](https://github.com/tkem/cachetools) 重跑——完全不同的领域（缓存容器 vs 字符串解析），完全不同类型的 bug（状态更新 vs 输入解析）。

那个 bug 是：用一个「已经过期」的存活时间去覆盖一个**已存在的键**时，旧值仍然可读。

触发它需要「**对已经存在的键再次赋值**」。`__setitem__` 里处理「新键」和「已存在键」本来就是两个分支，bug 只在后者。

**只测首次写入，杀伤率再高也碰不到。**

## 所以这两个指标到底测什么

| | 变异杀伤率 / 覆盖率 | 真实缺陷检出 |
|---|---|---|
| 衡量的是 | 单点改动的敏感度 | 能否构造出触发缺陷的**输入组合与路径** |
| 高的条件 | 用例铺得密 | 用例铺得**对** |
| 提升方式 | 多写用例 | 想对了该测什么 |

**密和对，是两回事。** 你可以写一千个用例把杀伤率堆到 90%，同时一个真 bug 都发现不了——实验里这事真实发生了。

## 那该怎么办

**第一，别拿覆盖率当质量结论。** 它可以当**下限门禁**——覆盖率过低说明测试确实不够——但它高不代表质量好。「覆盖率 80% 达标」这句话里，「达标」指的是没有明显漏测，不是「没有 bug」。

**第二，补上两类它测不到的东西：**

**① 特征交叉。** 列出输入的特征维度，然后构造维度之间的两两组合。**重点是两个「本身就是特殊情况」的取值叠加**——单独看都正常，凑一起才出问题。

**② 特征的进入路径。** 对每个特征问：它有几种方式进入这个函数？

- **路径 A**：由参数控制产生 → 走的是「生成」逻辑
- **路径 B**：由输入数据自带，或由对同一对象的重复操作、时间推进引入 → 走的是「解析 / 更新」逻辑

**同一个特征走两条路径，函数内部往往是两套完全不同的代码。** 只测一条，另一条的缺陷永远发现不了。

上面两个项目的 bug，都藏在路径 B 里。这不是巧合——「初始化/生成」和「更新/解析」分成两套代码，是写代码这件事本身的结构，哪个项目都成立。

**第三，如果你在用 AI 生成测试**，把上面两条写进 prompt。实验里这两条指令让真 bug 检出从 0 变成了 17 个。代价是用例数涨 2–3 倍，误报也会增加。

## 边界

- 样本只有 2 个项目，**只验证了「能命中已知 bug」，没验证「能发现未知 bug」**——后者要在活跃项目上长期跑才说得清
- 没有在并发、异步、性能类 bug 上验证过
- 变异杀伤率的下降有混淆因素：算杀伤率前要排除误报用例，各轮排除数量不同，剩余测试集大小不一样

这些限制我写在明面上，因为**藏起来的话，第一个照着做的人就会踩坑**。
