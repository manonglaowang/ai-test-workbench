
# 我让 AI 写了 2392 个测试用例，前三轮一个 bug 都没抓到

## 一、先回答：别照搬 Web 那套，按层切

我是**码农老王（王祥）**，在深圳做**软件质量保障**，方向是消费电子和 AI 硬件的自动化测试体系建设。公众号「**码农老王聊AI**」。

这篇讲两件事：**AI 生成测试用例到底行不行**，以及**怎么让它行**。

结论先放：我做了四轮对照实验，前三轮 AI 一共写了 1373 个用例，**真 bug 零命中**；第四轮改了 prompt，命中 17 个。差别只在三条指令。

顺带还撞出一个反直觉的结果：**变异杀伤率最高的两轮，恰恰是一个 bug 都没抓到的两轮。**

如果你做 Web 或接口测试，现在的答案很成熟。Playwright MCP、browser-use、TestSprite 往 Cursor 或 Claude Code 里一挂，Agent 从读代码到生成用例、写脚本、执行、失败自愈，一条链自己跑完。TestSprite 官方称能把 AI 生成代码的一次通过率从 42% 提到 93%（[厂商自测数据](https://www.prnewswire.com/news-releases/testsprite-2-0-aims-to-solve-ai-code-quality-crisis-with-its-new-mcp-server-302505031.html)，看看就好）。

但你要是测设备——固件、嵌入式、蓝牙、需要真机和串口的东西——这套照搬会撞墙。

核心原因就一条：**Web 的环境可以重置，设备的不行。**

| | Web / 接口 | 设备 / 固件 |
|---|---|---|
| 环境获取 | 起个容器，秒级 | 真机、夹具、串口、烧录 |
| 状态重置 | 一条命令回到干净态 | 可能要重新烧录，甚至人工干预 |
| 试错成本 | 近似为零 | 一次失败可能砖一块板子 |
| 并发 | 水平扩容 | 手上有几台就是几台 |
| 时序敏感 | 弱 | 强，毫秒级问题很常见 |

Agent 全自动的隐含前提是**可以廉价地试错**。这个前提在设备层不成立。

所以别指望端到端交给 AI。按层切：

```
┌──────────────────────────────────────┐
│  物理环境层                     → 人  │
│  真机 / 夹具 / 串口 / 烧录 / 环境搭建  │
├──────────────────────────────────────┤
│  用例与脚本层                   → AI  │
│  用例生成 / 脚本编写 / 维护 / 日志分析 │
└──────────────────────────────────────┘
```

**人搭环境，AI 处理用例脚本。**

一句话，但它决定了后面所有事怎么安排。

## 二、讲标准：哪一层能交给 AI，看三个问题

不是所有环节都适合。我用三个问题筛：

**试错成本是不是接近零？**
脚本写错了 Ctrl+Z，烧错固件可能要返修。成本不对称，授权就该不对称。

**产物能不能进版本库、能不能 review？**
用例和脚本进 Git，diff 看得见，错了能回滚。物理环境的状态进不了版本库。

**失败了能不能自动重试？**
脚本挂了重跑一次几秒钟。设备卡死了得有人去按复位键。

三个都是「是」，交给 AI。有一个是「否」，人来兜底。

按这套往下拆：

| 环节 | 归属 | 依据 |
|---|---|---|
| 规格 → 测试点提取 | AI 主导，人评审 | 纯文本，可 diff |
| 测试用例生成 | AI 主导，人评审 | 同上，但业务合理性必须人过 |
| 自动化脚本编写 | AI 主导 | 可版本化、可回滚 |
| 脚本维护（接口变更后修） | AI 主导 | 纯重复劳动 |
| 日志分析与失败归因 | AI 辅助，人决策 | AI 给假设，人验证 |
| 测试报告生成 | AI 主导 | 纯文本 |
| **测试环境搭建** | **人** | 物理成本，不可重置 |
| **烧录 / 夹具 / 上电** | **人** | 试错有硬件损耗 |
| 执行调度 | CI | 传统能力，不需要 AI |

注意最后一行。很多人把「AI 测试」和「自动化测试」搞混了——**调度、并发、报告归档这些事，Jenkins 十年前就能干，不需要大模型。** AI 该去的地方是原来必须人写、且写起来很烦的那部分。

## 三、给证据：我做了个实验，结果跟我预想的不一样

方法论说完了。但只讲判断不给数据，跟那堆「AI 测试十大工具」的口水文没区别。

所以我做了个可复现的对照实验。**代码全部开源，你可以自己跑一遍验证。**

### 实验设计

挑一个真实开源项目 —— [pypinyin](https://github.com/mozillazg/python-pinyin)（汉字转拼音，MIT，5.3k star）。
把代码 checkout 到一个**已知 bug 修复之前**的版本，让 AI 生成测试用例，看它能不能发现那个三周后才被修复的 bug。

| 项 | 值 |
|---|---|
| 实验 commit | `a8878ec`（2022-12-24，bug 仍存在） |
| 修复 commit | `05eacb3`（2023-01-14，"Fixed #290"） |
| bug 本质 | 正则字符类漏了 `ü`：`[aeoiuvnmê]` → `[aeoiuvnmêü]` |

**盲测纪律**：不告诉 AI 有 bug、不提 issue、不提「ü」和「边界」这类引导词、不给修复后代码、禁止联网检索该项目。只给源码和 docstring。

先说一个我没想到的前置事实：**项目自带的 141 个测试，在这个 bug 版本上全部通过。** 维护者自己的测试套件也没抓到。

### 结果一：AI 一个 bug 都没发现

AI 生成了 979 行、84 个测试函数、426 个参数化用例，语法可执行率 100%。

| | bug 版本 | 修复版本 |
|---|---|---|
| 失败 | 7 | **9** |
| 通过 | 419 | 417 |

判定方法很简单：**把同一套测试拿到修复版上再跑一遍**。真发现了 bug 的用例，修复后应该变绿。

结果那 7 个失败在修复版上照样失败 —— **全是误报**，是 AI 自己把期望值写错了，跟 bug 无关。

**命中 issue #290 的用例：0 个。**

### 结果二：更糟的是，AI 把 bug 写成了规范

注意上面那个表：修复版反而多了 2 个失败。这 2 个测试在 bug 版本上是绿的。

```python
# AI 生成的断言
assert to_tone3('sha5ng') == 'shang5'   # ← 这是 bug 行为
# 修复后的正确行为
to_tone3('sha5ng') == 'shang'
```

**如果把这套 AI 生成的测试当成回归套件，维护者真正的 bug 修复，会被判定为「回归失败」。**

这个后果比"没发现 bug"严重得多 —— 没发现只是没帮上忙，固化成规范是主动阻碍修复。

### 结果三：但它确实"看到"了根因

有意思的是，AI 在自评风险时写了这么一句：

> "`to_tone2`/`to_tone3` 对含 `ü` 输入的处理依赖 `RE_TONE3` 的 `[a-zê]` **不匹配 `ü`** 这一细节"

**它准确定位到了引发 bug 的那个正则**，但把它理解成了「设计如此」，而不是缺陷。

### 结果四：覆盖面它是真的强

我又跑了一轮变异测试 —— 往源码里注入 37 个单点变异（`>` 改 `>=`、删边界判断、改索引等），看测试集能杀掉多少。

| 测试集 | 用例数 | 变异杀伤率 |
|---|---|---|
| 项目自带（维护者手写） | 141 | **56.8%** |
| AI 生成（排除 7 个误报后） | 419 | **81.1%** |

**AI 高出 24.3 个百分点。** 这个提升是实打实的。

### 于是我又做了三轮

run01 的结果让我下了个结论：**AI 的期望值是从代码推导的，不是从意图推导的**。听起来很顺，那就该有个推论——**不给源码、只给规格呢？**

于是有了后面三轮。**每一轮只改一个变量**，规格文件三轮 md5 完全一致。

| | run01 | run02 | run03 | run04 |
|---|---|---|---|---|
| 输入材料 | 源码 | 规格 | 规格 | 规格 |
| 指令①「给规格」 | ❌ | ✅ | ✅ | ✅ |
| 指令②「维度交叉」 | ❌ | ❌ | ✅ | ✅ |
| 指令③「进入路径」 | ❌ | ❌ | ❌ | ✅ |
| 展开用例 | 426 | 448 | 499 | **1019** |
| **命中真 bug** | ❌ 0 | ❌ 0 | ❌ 0 | ✅ **17** |
| 误报 | 7 | 2 | 17 | 6 |
| 把 bug 固化成规范 | 🔴 2 | ✅ 0 | ✅ 0 | ✅ 0 |
| 变异杀伤率 | 81.1% | 81.1% | 51.4% | 67.6% |

**三条指令缺一不可**：只有①→0 命中；①+②→0 命中；**①+②+③→命中**。

### run02：给规格解决了「固化 bug」，但没解决命中

只给函数签名和文档、拿掉全部实现之后：误报从 7 降到 2，**把 bug 写成期望值的从 2 处降到 0** —— 期望值来自规格，就不会把当前实现的错误行为当成正确答案。

**但真 bug 照样 0 命中。** 我那个「期望值来源」的解释，被自己的实验推翻了。

### run03：问题在「维度交叉」，但只解决了一半

我去查两轮测试**实际覆盖了哪些输入**：

| | 含 `ü`/`v` 的输入 | 含轻声 `5` 的输入 | **两者同时** |
|---|---|---|---|
| run01 | 42 种 | 6 种 | **0** |
| run02 | 52 种 | 9 种 | **0** |

单维度铺得很宽，**交叉是零**。而 bug 的触发条件恰恰是两个特征同时出现（`lün5`）。

于是 run03 明确要求：枚举特征维度，构造两两交叉。

有效——ü+5 的交叉输入从 0 变成 6 个（`lv5` `lve5` `lü5` `nv5`…）。这些输入**确实触发 bug**：`to_tone2('lv5')` 在两个版本返回不同结果。

**但还是 0 命中。** 因为方向错了：

```python
to_tone2('lv', neutral_tone_with_five=True) == 'lv5'   # 输入不带5，参数生成5
```

AI 生成了 `'lv5'` 这个字符串，**却从头到尾只当期望值用，一次都没当输入喂进去。**

### run04：真正的盲区是「特征从哪条路进来」

第三条指令补上了这个：

> 对每一个特征，问它有几种方式进入这个函数。
> **路径 A：由参数控制产生。路径 B：由输入数据自带。**
> 同一特征走两条路径时，函数内部很可能是「生成」和「解析」两套完全不同的代码。

run04 的 AI 主动做了这个区分，还给测试函数加了 `_path_a` / `_path_b` 后缀。命中的 17 个用例里，有三条正是「输入同时自带 v 和 5」：

```python
@pytest.mark.parametrize('src, expected_v, expected_u', [
    ('lv5',   'v',  'ü'),
    ('lve5',  've', 'üe'),
    ('nve5',  've', 'üe'),
])
def test_finals_v_and_five_both_from_input_path_b(src, expected_v, expected_u):
    """路径 B×B：输入同时自带 v 和 5。"""
```

为什么是这条路径？因为 issue #290 的根因是一个正则漏了 `ü`，而**那个正则只在解析输入时才被调用**。前三轮全部只覆盖「参数产生」那条路，所以再怎么加覆盖、再怎么做交叉，都碰不到它。

**输出侧的生成逻辑和输入侧的解析逻辑，通常是两套代码。只测一侧，另一侧的缺陷永远发现不了。** 而解析类 bug 恰恰是最常见的一类。

### 反直觉的副产物：杀伤率和「能发现 bug」是两回事

回头看那张表最后两行：

| | 变异杀伤率 | 真 bug 命中 |
|---|---|---|
| 项目自带 141 个测试 | 56.8% | 0 |
| run01 / run02 | **81.1%**（最高） | **0** |
| run03 | 51.4% | 0 |
| run04 | 67.6% | ✅ **17** |

**杀伤率最高的两轮，一个 bug 都没抓到；抓到 17 个的那轮，杀伤率只排第二。**

原因不难理解：变异测试注入的是**单点变异**（改个比较符、删个分支），考的是单维覆盖密度；而真实 bug 藏在**多特征交叉 + 特定进入路径**上，是另一个维度的能力。

**这两个指标测的不是同一件事，高的那个不保证低的那个。** 任何拿覆盖率或杀伤率当质量门禁的团队，都值得看一眼这张表。

## 四、做比较：现有方案的 AI 都放在哪一层

| 方案 | 覆盖 | AI 落点 | 设备层 |
|---|---|---|---|
| [MeterSphere 3.6.4+](https://blog.fit2cloud.com/?p=1a711e42-04fe-4dce-8196-938071be4021) | Web / App / 接口 | 文档生成用例 | 未覆盖 |
| 蚂蚁 TestAgent 等测试大模型 | 通用软件测试 | 用例生成 | 未覆盖 |
| TestSprite / Playwright MCP | Web / E2E | 全链路 Agent | 未覆盖 |
| browser-use / Midscene / Skyvern | 浏览器 GUI | 视觉驱动执行 | 未覆盖 |
| 本文思路 | 设备类测试 | **用例脚本层** | 覆盖 |

这些方案都很好，别误会。它们不覆盖设备层，是因为**它们的目标用户不需要**。做 Web 的人手上没有串口和夹具。

但做硬件的人绕不开。而且我检索了一圈，中文社区里的「一体化测试平台」——[TesterHome 上的 ATP](https://testerhome.com/articles/25871)、开源的 [AutoZone](https://github.com/Wesly-Yu/AutoZone) 之类——覆盖边界基本都停在 Web + App + 接口。固件那一层，在我查到的公开方案里都没进过边界图。

**所以关键差异不在「用了什么 AI」，在「AI 被放在哪一层」。**

## 五、讲边界：这套不适合谁，以及我判断错过的地方

### 不适合的情况

- **纯 Web / SaaS 业务**：没有设备层，直接上 Agent 全自动更快，本文的分层是多余的约束
- **没有自动化基础的团队**：AI 是放大器不是起点。CI 都没有的话，先把流水线搭起来
- **指望全自动的人**：这套方法的前提就是承认有一层必须人来做

### 明确不能干的事

- AI 生成的用例**必须人工评审业务合理性**。测试场景也会幻觉——模型会编出逻辑自洽但业务上不存在的场景，而且编得很像真的
- 别让 AI 直接触碰烧录、上电、夹具控制这类物理操作
- 别拿「AI 生成了 300 条用例」当成果。**没被评审过的用例不是资产，是负债**
- 别拿变异杀伤率或覆盖率当质量结论。实验里 81.1% 的杀伤率和「0 个 bug」是同时成立的
- 三条指令不是万能药。样本只有 2 个项目，而且**只验证了「能命中已知 bug」，没验证「能发现未知 bug」**——后者要在活跃项目上长期跑才说得清

### 我判断错过的地方

说个打脸的。

我一开始跑出来的杀伤率是 **46.7%**，正准备写进文章。临发前多做了一步：**同一个实验再跑一遍**。

第二次 50.7%。第三次 49.3%。第四次 48.0%。

同一份代码、同一套测试、同一台机器，四次四个数。**我的测量工具本身是坏的。**

查下来两个 bug，第二个特别隐蔽：

**bug 1：我把文档字符串也变异了**

变异引擎按行做正则替换，结果把中文 docstring 里的 `False`、`and` 当成代码给改了：

```
L121: "当为 False 时结果中将使用 ``v`` 表示 ``ü``"
```

改字符串内容不影响行为，这叫「等价变异体」，本该排除。**75 个变异体里有一半是这种噪音。**

改用 `tokenize` 逐 token 判定后，变异体从 75 降到 37。

**bug 2：跑的根本不是当前变异体**

修完 bug 1 还是不稳。定位到两个反复翻转的变异体，其中一个是：

```python
def _v_to_u(pinyin, replace=False)  →  replace=True
```

想了很久才反应过来：**CPython 的 `.pyc` 缓存失效判据是「源文件 mtime（秒级）+ 文件大小」**。

我的引擎连续写入变异体，而 `False`→`True` 正好是 -1 字节。**两个不同的变异体字节数相同、又落在同一秒内写入，解释器就复用了上一个的 `.pyc`** —— 跑的不是当前变异体。

加个 `PYTHONDONTWRITEBYTECODE=1` 就好了。修完连跑三次，稳定在 56.8%。

**这件事的教训比实验结论本身更值得记：**

> 我差点把一个不可复现的数字发出去。
> 而且讽刺的是——**这篇文章讲的就是"AI 生成的测试不可信，要人工验证"，结果我自己写的验证工具也不可信。**
> 自己写的测量工具，同样需要被测量。

如果没有「同一实验重复跑一遍」这个动作，上面所有数字都是废的。

**还有一次打脸，是结论层面的。**

run01 跑完，我给出的解释是「AI 的期望值从代码推导，所以看不见 bug」。写得挺顺，我当时觉得挺有道理。

然后 run02 换成只给规格——**照样 0 命中**。解释直接被自己的实验推翻。

真正原因是组合覆盖为零，跟期望值从哪来关系不大。**如果我 run01 之后就收工发文章，发出去的就是一个错误结论**，而且因为它听起来合理，大概率没人会质疑。

> 一个实验只能证伪，不能证实。
> **想让结论站得住，得设计一个「如果我错了，这个实验会打我脸」的对照组。**

### 其他几条

- **AI 生成用例最容易错的地方，是那些「需要从多个源文件交叉推导」的行为。** 7 个误报全部集中在标调位置规则（`iou`/`uei`/`uen` 的声调标在哪个字母上）——这个规则的定义分散在常量表和多个函数里，AI 推导链一长就出错。
- **上下文够用，不是瓶颈。** 668 行源码一次读完毫无压力，生成 979 行测试也很快。瓶颈从来不是"能不能读完"，是"读完之后判断对不对"。
- **别用 AI 生成的测试当回归基线。** 这是本次实验最实际的一条。它会把当前行为固化成规范，包括当前的 bug。

## 六、给行动：三条指令，你可以直接抄

这是四轮实验换来的东西。每一条都有一轮实验证明它必要。

```
① 只给规格文档和函数签名，不要给实现源码。
   期望值必须来自「按规范这个函数应该返回什么」，
   而不是「这段代码会返回什么」。

② 枚举输入的特征维度，并构造维度之间的两两交叉。
   特别注意两个「本身就是特殊情况」的取值叠加在一起的情况。

③ 对每一个特征，枚举它进入函数的路径：
   - 路径 A：由参数控制产生
   - 路径 B：由输入数据自带
   同一特征走两条路径时，函数内部很可能是「生成」和「解析」两套代码。
   必须分别构造用例，并把「已经自带该特征的数据」直接作为输入传进去。
   若某特征既能由参数产生、又能出现在输入串里，两条路径都必须测。
```

**换个项目还成立吗？我又跑了一轮。**

前四轮都在 pypinyin（汉字转拼音）上做，结论有个明显软肋——可能只是对这一个项目、这一个 bug 有效。

于是换 [cachetools](https://github.com/tkem/cachetools)（缓存容器库）重跑，**指令一字未改**：

| | pypinyin | cachetools |
|---|---|---|
| 领域 | 字符串解析 | 数据结构 / 状态管理 / 时间语义 |
| bug 类型 | 输入解析缺陷 | 状态更新缺陷 |
| **命中真 bug** | ✅ 17 | ✅ **1** |
| 误报 | 6 | 2 |
| bug 固化 | 0 | 0 |

命中的用例叫 `test_tlru_overwrite_with_already_expired_ttu_pathB`——**又是指令③产出的**。

cachetools 这个 bug 的触发条件是「**对已经存在的键再次赋值**」。`__setitem__` 里处理「新键」和「已存在键」是两个分支，bug 只在后者。只测首次写入，永远碰不到。

> **两个项目、两种完全不同的 bug，命中它们的是同一条指令。**
> 因为「初始化/生成」和「更新/解析」是两套代码——这个结构在哪个项目里都成立。

**各自解决什么**：

| 指令 | 解决的问题 | 实验证据 |
|---|---|---|
| ① 给规格 | AI 把 bug 当成正确行为 | 固化 2 处 → 0 |
| ② 维度交叉 | 只测单个特征，不测组合 | ü+5 交叉输入 0 → 6 |
| ③ 进入路径 | 只测生成侧，不测解析侧 | 真 bug 0 → **17 命中**；换项目再命中 1 |

**代价要说清楚**：用例数从 426 涨到 1019（2.4 倍），token 成本相应上升。误报也会增加——run03 一度涨到 17 个，因为系统性构造交叉时 AI 要对更多「规范没明说」的边界做推断。

**然后是仍然需要人做的部分：**

**评审业务合理性。** AI 生成的用例必须人工过一遍。测试场景同样会幻觉——模型会编出逻辑自洽但业务上不存在的场景，而且编得很像真的。

**别拿 AI 生成的测试当回归基线。** 尤其在只给源码的情况下，它会把当前行为（包括当前的 bug）固化成规范。run01 那 2 个用例如果进了 CI，维护者真正的修复会被判定成「回归失败」。

**别用覆盖率或杀伤率下结论。** 上面那张表已经说明问题了。

**如果你测的是设备类**，前面讲的分层依然成立：物理环境层自己搭，用例脚本层交给 AI，配上这三条指令。设备测试的用例往往有更多维度（固件版本 × 硬件批次 × 网络状态 × 电量），交叉和路径这两条只会更重要。
